Shane Melaugh 称用 Gemini 4 Argon 分析 1400 个 Claude Code 会话后发现，11 月 3 日 Opus 5.5 的推理方式明显改变，模型名未变但 high 档投入的推理量骤降。他举例说 high 档在真实 bug 上急着动手、三小时无解，而 xhigh 档思考几分钟便找到修复。他承认这不是严谨基准，只是个人挫败感引发的观察。

社区讨论

  • 有评论认为这更像容量约束而非恶意：新模型上线前把旧模型塞进更小的资源池；若厂商工程师公开否认量化，应当被采信。
  • 反方强调人类认知偏差：同一模型的输出方差本就很大，建议自备一组有代表性的任务反复跑，才能分清噪声与真实退化。

这是 ISO C++ 标准提案 P4454R0，标题指向语言创造者与标准所有者之间的严重分歧。讨论很快转向“谁拥有 C++”这一根本问题：是写标准的委员会，还是实际实现标准的编译器与使用它的开发者。

  • 一派认为没人拥有语言，委员会只拥有标准，开发者会选实用的做法；另一派反驳说标准就是语言，没有治理机构只会导致分裂或停滞。

  • export 等历史遗留问题被拿来佐证：各大编译器长期各有各的实现，标准与实现从未完全重合。

10对 GPUI 的批评：状态模型走不远
120 分 ｜ 87 评论 ｜ 已读原文 ｜ blog.zortax.de
https://blog.zortax.de/posts/a-critique-of-gpui

作者认为 GPUI 与 egui 的状态模型对复杂桌面应用是死路：GPUI 的 notify 只能告诉框架某个 entity 变了，却不知道哪个字段变了，于是大量视图被重绘。他的基准显示，3000 行列表改一个标签在缓存视图下要 8.4 毫秒，写成普通元素则要 92 毫秒，而手写相等判断能把一次等值写入从 7.9 毫秒降到 0.9 微秒。

社区讨论
  • 有人拿 Adobe 类复杂应用反问那它们为何能用，回答是 CAD 类界面可见控件通常只有几百个，且渲染与 UI 分离，复杂度不可类比。
  • 也有人指出不少新 GUI 是 vibe code 出来的，状态管理被丢给黑箱，性能问题只是被推迟。
  • 作者在文中承认自己参与竞品 zgui，并移植过 GPUI 的 Linux 渲染器，读者因此提醒要打折看待其结论。
